# REPORT: Улучшение контракта API (Задача 2)

## 1. Текущий уровень зрелости API

Текущий контракт использует несколько URI (`/room`, `/add-room`, `/booking`)
и HTTP-методы (`GET`, `POST`), но имена ресурсов частично отражают действия,
а не сущности. Гипермедиа-ссылки отсутствуют. По модели зрелости Ричардсона
это примерно уровень 1–2 (ресурсы + методы HTTP без HATEOAS). 

## 2. Замечания к текущему контракту

- В именах endpoint используются глаголы (`/add-room`), что больше похоже
  на RPC, чем на REST-ресурсы. 
- Ресурсы `room` и `booking` смешивают сущности и действия.
- Имена параметров не единообразны (`guestNum` / `guestsNum`).
- При создании ресурсов всегда возвращается 200, хотя по REST
  корректнее использовать 201 Created. 

## 3. Предложенные изменения

### 3.1. Имена ресурсов и методов

- Заменить:
  - `GET /room` → `GET /rooms`
  - `POST /add-room` → `POST /rooms`
  - `POST /booking` → `POST /bookings`
- Использовать существительные во множественном числе (`rooms`, `bookings`)
  и методы HTTP как глаголы (GET, POST, PUT, DELETE). 

### 3.2. Параметры запросов

- Для поиска свободных комнат:
  - `GET /rooms?checkIn=20210308&checkOut=20210311&guests=2`
- Привести имена к единому стилю: `guests` вместо `guestsNum`/`guestNum`.

### 3.3. Коды ответов и формат

- Для создания комнаты и бронирования:
  - использовать статус 201 Created и возвращать созданный ресурс
    в теле ответа. 
- Для ошибок использовать единый формат:
  ```json
  {
    "error": "Room already booked",
    "code": "ROOM_ALREADY_BOOKED"
  }
  ```

## 4. Изменённая Postman-коллекция

- Создана новая коллекция `hotel-api-v2` с ресурсами:
  - `GET /rooms`, `POST /rooms`
  - `POST /bookings`
- В коллекции отражены новые URI, параметры и ожидаемые ответы.
Коллекция демонстрирует контракт API с более высоким уровнем зрелости
(уровень 2 модели Ричардсона).
